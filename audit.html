Projektportrait

Shadow Objects ist ein reaktives Entity-Component-Framework für den Browser. Es trennt Anwendungslogik von ihrer Darstellung: das DOM spannt nur noch einen Entity-Baum auf, die Logik selbst läuft als Shadow Objects in einer Shadow Environment — wahlweise im Main Thread oder vollständig in einem Web Worker, ohne dass sich der Logikcode dabei ändert. Drei Custom Elements (<shae-worker>, <shae-ent>, <shae-prop>) sind die gesamte DOM-seitige Oberfläche; zwischen beiden Seiten läuft ein asynchrones Protokoll aus serialisierten Change Trails.

Das Monorepo führt vier Packages: die Kernbibliothek, eine publizierte Referenzanwendung (Offscreen-Canvas-Rendering mit three.js im Worker) und zwei nicht publizierte Testpakete. Das Projekt bezeichnet sich selbst als hochexperimentell; die Versionsstände — 0.33.0 und 0.6.0 — bestätigen das.

Der Bereich hat keinen high-Befund mehr. Das Gewicht tragen zwei mittlere: die Zusage von clearOnDestroy, die auf dem Weg „Shadow Object verlässt die Konstruktorenmenge" keinen Konsumenten erreicht, obwohl die Dokumentation sie jedem verspricht, und createEntity(), das die Entity registriert, bevor ihre Shadow Objects stehen — wirft einer der Konstruktoren, bleibt sie halbfertig im Worker-Kernel zurück, dem View unbekannt und von keinem Aufräumweg erreicht.

Darunter wird es ruhig. Fünf Befunde hängen an einer einzigen ungeklärten Frage — ob zwei ViewComponent in einem Context dieselbe uuid tragen dürfen; heute erzeugt dieser Fall eine Entity, die niemand mehr abbaut. Dazu zwei Konstruktoren, die aus dem Rahmen fallen, und eine Handvoll Halbkanten, die über die heutigen Pfade unerreichbar sind und beim nächsten Umbau an derselben Stelle zur Falle werden.

Offene Fragen

Darf eine uuid in einem ComponentContext zweimal vergeben werden?

Fünf Befunde hängen an dieser einen Antwort — BUG-002, CONS-003, CONS-004, CONS-005 und mittelbar API-001. Lautet sie „nein", genügt ein Wächter in addComponent(), und alle fünf fallen ohne weiteren Umbau. Lautet sie „ja", braucht der Context durchgehend die Instanz als Identität statt der uuid, und die vier Stellen sind je ein eigener Zug mit eigener Gegenprobe. Der Code entscheidet die Frage heute an jeder Stelle einzeln, und nicht überall gleich.

Optimierungspotenzial

Kein Defekt, keine Backlog-Zeile — Stellen, an denen sich Arbeit auszahlt, ohne dass etwas kaputt wäre.

Eine Entscheidung schließt fünf Befunde

Der uuid-Cluster ist der einzige Ort im Backlog, an dem eine Zeile Wächtercode fünf Einträge erledigt. Wer aufräumen will und wenig Zeit hat, fängt dort an, nicht bei den vier Konsistenz-Einträgen einzeln.

Coverage als Instrument, nicht als Note

Die Suiten sind dicht genug, dass eine Coverage-Messung kein Armutszeugnis ausstellen würde. Ihr Wert liegt woanders: sie zeigt einem Remediation-Lauf, welche der neu berührten Zweige noch kein Wächter hält — heute muss man das raten.

Eine Re-Request-Runde je Task statt je Entity

Die beiden Re-Request-Kanäle kosten quadratisch, und der Code sagt das mit Zahlen dazu: 600 Wurzeln in einem Namespace verbringen rund 270 ms in einem Aufbau, der ohne den Kanal etwa 20 ms braucht. Eine gemeinsame Runde für alles, was im selben Task verbindet, wäre der eine Umbau, der den quadratischen Term entfernt.
